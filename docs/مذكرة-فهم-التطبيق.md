# مذكرة فهم ومراجعة تطبيق المحادثة

هذه المذكرة تشرح التطبيق كما هو منفّذ في الشيفرة: كيف يبدأ الطلب، وكيف يعمل تسجيل الدخول، وكيف تُخزّن الرسالة وتُرسل، وكيف تصل التحديثات إلى المستخدمين، وما الذي لا يحفظه النظام حاليًا. ادرسها مع فتح الملفات المشار إليها، لا كبديل عن الشيفرة.

## 1. ملخص المشروع في دقيقة

هذا تطبيق محادثة عامة بغرفة واحدة. له واجهتان تستخدمان مجال العمل نفسه:

1. **واجهة متصفح** مبنية بـLaravel وLivewire وBlade، وتدخل بحساب Google ثم تحتفظ بتسجيل الدخول في جلسة المتصفح.
2. **REST API** للعملاء الخارجيين، وتستخدم Google OAuth للحصول على رمز Sanctum من نوع Bearer.

تُخزّن الرسائل والمستخدمون في PostgreSQL في التشغيل المعتاد. عند إرسال رسالة، يتحقق التطبيق من النص والمستخدم، ويحفظها عبر Eloquent، ثم يبث حدثًا خاصًا عبر Reverb إلى المتصلين. الاختبارات تستبدل قاعدة التشغيل بقاعدة SQLite داخل الذاكرة وتوقف البث.

**النقطة الأهم:** الرسائل محفوظة، لكن الردود والتفاعلات الموجودة الآن هي معاينات واجهة مؤقتة؛ لا توجد جداول لها ولا تبقى بعد تحديث الصفحة.

## 2. صورة ذهنية للبنية

```text
المتصفح
  ├─ صفحة الدخول / المحادثة
  │    └─ Livewire + Blade
  │         └─ MessageService / GoogleAuthService
  ├─ JavaScript + Laravel Echo
  │    └─ اتصال WebSocket إلى Reverb
  └─ جلسة المتصفح + CSRF

عميل خارجي
  └─ REST API
       ├─ Bearer token من Sanctum
       ├─ Form Request للتحقق
       ├─ Controller لتنسيق HTTP
       ├─ Service لقواعد استخدام الرسالة
       ├─ Eloquent للوصول إلى قاعدة البيانات
       └─ API Resource لشكل JSON

MessageService ── ينشئ أحداث ShouldBroadcast ──> Reverb ──> Echo لدى المشتركين
```

### قاعدة تنظيم الكود

- **Route** يحدد عنوان الطلب والحماية.
- **Middleware** ينفذ عملًا مشتركًا قبل/بعد الطلب، مثل المصادقة أو اختيار اللغة.
- **Form Request** يتحقق من مدخلات HTTP.
- **Controller** يربط الطلب بالعمل المطلوب ويعيد استجابة HTTP؛ لا ينبغي أن يحمل منطق الدردشة كله.
- **Service** يضم حالات الاستخدام المشتركة بين API وLivewire.
- **Model** يمثل البيانات والعلاقات ونطاقات الاستعلام.
- **Policy** يقرر هل يملك المستخدم صلاحية تعديل أو حذف الرسالة.
- **Resource** يحدد البيانات التي تظهر في JSON أو حدث البث.
- **Event** يصف تحديثًا يرسَل إلى المشتركين.
- **Blade / Livewire / JavaScript / CSS** تعرض الواجهة وتدير تفاعل المستخدم.

## 4. كيف يصل الطلب إلى التطبيق؟

يهيئ [`bootstrap/app.php`](../bootstrap/app.php) مسارات الويب والـAPI، ومسارات قنوات البث، ويضيف `SetLocale` إلى مجموعتي الويب والـAPI. كما يحدد أن `/api/*` يعيد JSON للأخطاء.

### طلب API نموذجي

```text
HTTP request
 → api middleware (ومنها locale وSanctum عند حماية المسار)
 → Form Request validation
 → MessageController
 → MessageService
 → Eloquent / PostgreSQL
 → MessageResource أو HTTP status
```

### طلب واجهة Livewire

```text
طلب الصفحة أو إجراء Livewire
 → web middleware + session authentication + locale
 → Chat component
 → MessageService / MessagePolicy
 → Eloquent
 → تحديث Blade عبر Livewire
 → Echo/Reverb لإبلاغ الجلسات الأخرى
```

الفصل مهم: API والواجهة لا تحتاجان لنسخ طريقة حفظ الرسالة. كلاهما يستعمل `MessageService`، بينما تختلف طريقة تسجيل الدخول والاستجابة.

## 5. تسجيل الدخول والأمان

### OAuth الخاص بالمتصفح

1. يفتح الزائر `/login` ثم يضغط «المتابعة باستخدام Google».
2. `AuthController::webRedirect` يطلب رابط Google من `GoogleAuthService`، ويمرر رابط العودة الخاص بالويب ورمز جلسة المتصفح كسياق للحالة.
3. الخدمة تنشئ `state` عشوائيًا بطول 40 محرفًا وتخزن بصمة SHA-256 لسياق الجلسة في Cache لمدة 10 دقائق.
4. بعد موافقة Google، يعود المتصفح إلى `/auth/google/callback` مع `code` و`state`.
5. الخدمة تسحب الحالة من Cache مرة واحدة (`pull`)، وتتحقق من بصمة جلسة المتصفح باستخدام `hash_equals`؛ منع إعادة استخدامها يمنع إعادة تشغيل callback.
6. Socialite يستبدل الرمز المؤقت مع Google من الخادم، وليس من JavaScript.
7. لا يقبل التطبيق الحساب إلا إذا وُجد Google ID والبريد وكان `email_verified` هو القيمة المنطقية `true`.
8. يُطابق المستخدم أولًا بـ`google_id`، ثم بالبريد الموثق بعد تطبيعه إلى أحرف صغيرة، وإلا يُنشأ مستخدم جديد.
9. يسجل Laravel الدخول في guard الويب، ويجدد معرّف الجلسة، ثم يوجه إلى `/chat`.

إذا فشل التحقق في تدفق الويب، يعاد المستخدم إلى صفحة الدخول برسالة مناسبة. أسرار Google تبقى في إعدادات الخادم ولا تُرسل إلى الواجهة.

### OAuth الخاص بالـAPI

1. يطلب العميل `GET /api/auth/google/redirect` ويحصل JSON فيه `url`.
2. يفتح المستخدم الرابط ويكمل موافقة Google.
3. يرسل العميل `code` و`state` إلى `GET /api/auth/google/callback`.
4. بعد التحقق يحصل العميل على `token`, `token_type: Bearer` وملف المستخدم.
5. يرسل الرمز في الطلبات المحمية:

```http
Authorization: Bearer <token>
Accept: application/json
```

حالة API عشوائية أحادية الاستخدام وبعمر 10 دقائق أيضًا، لكنها لا ترتبط بجلسة متصفح؛ لذلك لا تخلط تدفق API مع تدفق الويب. الخروج من API يحذف **الرمز المستخدم في الطلب الحالي**، وليس كل رموز المستخدم.

### حماية وخصوصية

- OAuth routes محددة بـ`throttle:20,1` أي 20 طلبًا في الدقيقة.
- إرسال Livewire محدود بـ30 رسالة في الدقيقة لكل مستخدم.
- لا تقبل الرسالة `user_id` من العميل كهوية للكاتب؛ الكاتب يأتي من المستخدم المصادق عليه في الجلسة أو Sanctum.
- `MessagePolicy` يمنع تعديل رسالة أو حذفها من غير صاحبها.
- `Message` لا يقبل عبر mass assignment إلا `content`.
- `UserResource` يعرض `id`, `name`, `avatar` فقط؛ البريد يعرض لملف المستخدم الحالي عبر `ProfileResource`.
- التحقق من المدخلات لا يغني عن الصلاحية: الأول يثبت أن المحتوى صالح، والثاني يثبت أن المستخدم مسموح له بالعملية.
- API الرسائل لا يعرّف حاليًا حدًا خاصًا به للمعدل؛ حد Livewire لا يعني تلقائيًا أن حد API يساويه.

## 6. قاعدة البيانات والعلاقات

### الجداول الأساسية

| الجدول | البيانات والدور |
|---|---|
| `users` | الاسم والبريد الفريد ومعرّف Google الفريد الاختياري والصورة وتاريخ التحقق وكلمة مرور اختيارية ورموز التذكر |
| `messages` | الكاتب `user_id`، المحتوى النصي، `created_at`, `updated_at`, و`deleted_at` للحذف الناعم |
| `personal_access_tokens` | رموز Sanctum المرتبطة بالمستخدم |
| `sessions` | جلسات Laravel عند استخدام session driver قاعدة البيانات |
| `cache`, `cache_locks` | Cache وأقفالها عند اختيار database cache |
| `jobs`, `job_batches`, `failed_jobs` | بنية Laravel للطوابير عند اختيار database queue |

الجداول المساندة موجودة في migrations، لكن استعمالها الفعلي يعتمد على إعدادات البيئة. ملف `.env.example` مضبوط على PostgreSQL وdatabase drivers للجلسة والـCache والـQueue. لا تنسخ أسرار `.env` إلى ملفات التوثيق أو Git.

### العلاقة

```text
User 1 ─────── * Message
Message.user_id → users.id (foreign key, cascade on delete)
```

`User::messages()` علاقة `hasMany`، و`Message::user()` علاقة `belongsTo`. عند حذف المستخدم نهائيًا، مفتاح قاعدة البيانات يحذف رسائله المرتبطة. أما حذف رسالة من التطبيق فهو soft delete: تُملأ `deleted_at` وتبقى الصفوف في قاعدة البيانات، بينما تستبعدها استعلامات Eloquent العادية.

يوجد فهرس على `created_at` وآخر مركب على `(user_id, created_at)` لدعم ترتيب القائمة وتصفية الكاتب. هناك فرق بين الحذف الناعم وحذف المستخدم cascade؛ لا تخلط بينهما.

### لماذا Resource؟

`MessageResource` يحصر استجابة الرسالة في:

```json
{
  "id": 42,
  "content": "مرحبًا",
  "user": { "id": 5, "name": "مستخدم", "avatar": null },
  "created_at": "2026-11-09T08:00:00+00:00",
  "updated_at": "2026-11-09T08:00:00+00:00"
}
```

بهذا لا تنكشف أعمدة قاعدة البيانات تلقائيًا، ويمكن تغيير تفاصيل التخزين دون إلزام العميل بكشفها. مورد المستخدم داخل الرسالة عام، أما البريد فيظهر في مورد الملف الشخصي للمستخدم نفسه.

## 7. دورة حياة الرسالة بالتفصيل

### التحقق من المحتوى

`SaveMessageRequest::contentRules()` هي مصدر قواعد النص المشترك:

- مطلوب.
- نص من نوع string.
- الحد الأقصى 2000 محرف.
- Laravel يزيل الفراغات الخارجية أثناء تهيئة الطلب؛ النص المكوّن من مسافات فقط يصبح غير صالح.

في Livewire يعاد استعمال القاعدة ذاتها عبر `validateOnly`. نجاح التحقق لا يحدد الكاتب ولا يمنح صلاحية التعديل.

### الإرسال من API

`POST /api/messages` → `SaveMessageRequest` → `MessageController::store` يأخذ المستخدم من Sanctum → `MessageService::send` ينشئ الرسالة ويحمل علاقة الكاتب → ينشئ `MessageSent` → يعيد Resource برمز `201`.

### الإرسال من Livewire

`Chat::send` يقص الفراغات، يتحقق من النص، يطبق rate limit، ثم ينادي `sendFromChat`. تحفظ الرسالة أولًا. الإرسال إلى قناة Reverb يؤجل لما بعد استجابة Livewire حتى لا ينتظر المستخدم اتصال البث. بعد ذلك يضيف المكون لقطة محلية للرسالة، يمسح المسودة، ويصدر حدث واجهة `message-sent`.

### التعديل

`PATCH /api/messages/{message}` أو إجراء Livewire:

1. إيجاد الرسالة؛ الرسالة المحذوفة ناعمًا تعامل كأنها غير موجودة.
2. التحقق من النص الجديد.
3. تمرير القرار إلى `MessagePolicy::update`.
4. إذا سمحت السياسة: `MessageService::update` يحفظ النص ويبث `MessageUpdated`.
5. المورد أو الواجهة يعرضان المحتوى ووقت التحديث. تستخدم الواجهة اختلاف `updated_at` و`created_at` لإظهار علامة «عُدلت».

### الحذف

المسار API يتطلب `MessagePolicy::delete`، وإجراء Livewire يستعمل فحص الصلاحية نفسه. `MessageService::delete` ينفذ soft delete ثم يبث حدثًا يحمل معرّف الرسالة فقط. لذلك لا يحتاج المستهلكون إلى نص الرسالة المحذوفة كي يزيلوها.

لا توجد معاملة قاعدة بيانات تجمع كتابة الرسالة وإرسال WebSocket في معاملة ذرية؛ البث وسيط منفصل ويمكن أن يتأخر أو يفشل بعد نجاح الحفظ. على الواجهة إظهار الأخطاء وعدم اعتبار حالة الاتصال اللحظي هي مصدر الحقيقة بدل قاعدة البيانات.

## 8. الترقيم والبحث والتصفية

### REST API

`GET /api/messages` يقبل:

- `page` عددًا صحيحًا يبدأ من 1.
- `user_ids[]` مصفوفة تصل إلى 50 معرّفًا صحيحًا موجبًا. تزال المكررات.

يعرض أحدث الرسائل أولًا، 10 في الصفحة، عبر `paginate`؛ لذلك يعيد Laravel روابط وبيانات مثل `meta.total`. لا يقبل هذا الـendpoint `per_page` أو البحث والتاريخ وفق `ListMessagesRequest` الحالي.

### واجهة المحادثة

`Chat` تعرض صفحة أولى من 10 رسائل. تستعمل `paginateForChat` و`simplePaginate`؛ فهذا يتجنب استعلام حساب العدد الكلي ويكتفي بمعرفة هل توجد صفحة أقدم. قاعدة البيانات تعيد الأحدث أولًا، ثم ترتب الواجهة عناصر الصفحة من الأقدم إلى الأحدث لتناسب قراءة المحادثة.

عند «تحميل الأقدم»، تدمج الصفحة الجديدة في أعلى السجل، وتزيل التكرار حسب ID، وتحافظ JavaScript على موضع التمرير. عند وصول رسالة جديدة، لا تفرض الواجهة النزول إلى الأسفل إن كان المستخدم يقرأ رسائل أقدم؛ يظهر زر للرسائل الجديدة.

المرشحات الموجودة في الواجهة تشمل النص والكاتب والتاريخ و«رسائلي فقط». يؤدي تغييرها إلى إعادة تحميل الصفحة الأولى. اختيار نطاق تاريخ غير مكتمل أو مقلوب يعرض خطأ ولا يحمّل نطاقًا مضللًا.

## 9. البث اللحظي: Reverb وEcho

### كيف تعمل القناة؟

- القناة `chat` قناة **خاصة** وليست عامة بلا تحقق.
- المتصفح يطلب تفويضها من `/broadcasting/auth` مع جلسة الويب وCSRF.
- العميل الخارجي يستخدم `/api/broadcasting/auth` مع Sanctum.
- `routes/channels.php` يسمح لأي مستخدم مصادق عليه بالانضمام؛ الغرفة عالمية مشتركة وليست قناة خاصة بكل مستخدم.
- ملفات المتصفح تهيئ Laravel Echo وPusher protocol للاتصال بـReverb؛ مفتاح التطبيق العام فقط يصل للمتصفح، لا سر Reverb.

### الأحداث

| اسم الحدث | المحتوى |
|---|---|
| `message.sent` | مورد الرسالة مع بيانات الكاتب العامة |
| `message.updated` | لقطة الرسالة بعد التعديل مع بيانات الكاتب العامة |
| `message.deleted` | `{ "id": 42 }` فقط |

الأحداث ترسل بـ`toOthers()` لتفادي تكرار ما أرسله نفس اتصال WebSocket. يلتقط `MessageEvent` نسخة payload عند إنشاء كائن الحدث، لا لاحقًا أثناء تنفيذه؛ هذا يمنع أن يعكس حدث «إرسال» تعديلًا أحدث حصل قبل بثه.

الواجهة تحدث المرسل محليًا مباشرة، وتحفظ IDs للرسائل التي أرسلتها لتجاهل Echo echo لنفس الرسالة. بقية المتصلين ينفذون `onMessageSent`, `onMessageUpdated`, `onMessageDeleted`.

### إعداد الشبكة

يوجد فرق بين:

- عنوان Reverb الذي يتصل به **خادم Laravel** (`REVERB_HOST`, `REVERB_PORT`).
- العنوان الذي يصل إليه **المتصفح** (`REVERB_PUBLIC_HOST`, `REVERB_PUBLIC_PORT`, `REVERB_PUBLIC_SCHEME`).

هذا الفرق مهم خصوصًا في Docker أو تشغيل التطبيق على الشبكة المحلية. جعل Laravel يستمع على `0.0.0.0` وحده لا يضمن أن WebSocket قابل للوصول؛ يجب أيضًا إعداد عنوان Reverb العام، و`APP_URL`، وURI رجوع Google، وفتح المنافذ اللازمة. لا تستخدم `php artisan serve` كخادم إنتاج.

**ملاحظة مراجعة قبل الإنتاج:** إعداد `config/reverb.php` في الشيفرة الحالية يحتوي `allowed_origins` بقيمة `['*']`. راجع تقييدها للنطاقات الموثوقة قبل نشر التطبيق للعامة.

## 10. الردود والتفاعلات: ما الموجود وما غير الموجود؟

### الموجود في الواجهة

- اختيار «رد» يحفظ حالة معاينة في `replyingTo` و`replyingToId`.
- عند الإرسال، يرفق المكون لقطة اقتباس مؤقتة في `replyContext` محلية، ويتحقق أن الهدف ما زال موجودًا.
- تعديل الرسالة الأصلية يحدث نص معاينة الاقتباس؛ حذفها يعلّم الاقتباس بأنه محذوف ويمسح نصه.
- توجد رموز تفاعل محددة مسبقًا؛ `toggleReaction` يضيف أو يزيل المستخدم الحالي من المصفوفة داخل حالة Livewire.
- `reactionSummary` و`selectedReactions` ينتجان شكل العرض وبيان ما إذا كان المستخدم الحالي قد تفاعل.
- تغيير رمز أو رد يعطيان تفاعلًا بصريًا في الصفحة.

### غير الموجود حتى الآن

- لا يوجد عمود `reply_to_message_id`.
- لا يوجد جدول للتفاعلات، ولا API لها.
- التفاعلات لا تبث كتحديث مستقل إلى المستخدمين الآخرين.
- سياق الردود والتفاعلات مؤقت وقد يختفي عند تحديث الصفحة أو انتهاء دورة Livewire.
- المورد وحدث الرسالة لا يتضمنان ردًا أو تفاعلات محفوظة.

إذًا، عند سؤال «هل الردود محفوظة؟» الجواب الدقيق: **لا، الموجود معاينة واجهة فقط**. لجعلها ميزة إنتاجية تحتاج مخطط قاعدة بيانات، علاقات وسياسات، API/تحقق، خدمة، أحداث بث، ترحيل بيانات إن لزم، واختبارات تزامن وصلاحية.

## 11. اللغة والمظهر والواجهة

- يستخدم التطبيق Blade وLivewire وCSS مخصصًا؛ لا يعتمد على Tailwind.
- أصول CSS مجزأة إلى tokens وbase وshell وauth وworkspace وchat وlocale وRTL.
- Vite يجمع `resources/css/app.css` و`resources/js/app.js` و`resources/js/chat-app.js`.
- حمولة Echo والـworkspace تُحمّل في مدخل الدردشة فقط، وليس صفحة تسجيل الدخول.
- اللغة المدعومة `en` و`ar`. أولوية الاختيار: جلسة، ثم cookie `chat_locale`، ثم تفضيل المتصفح، ثم لغة التطبيق. يضبط `SetLocale` أيضًا لغة Carbon.
- اتجاه الصفحة يتحول بين LTR وRTL، وملفات `rtl.css` تعالج الخصائص الفيزيائية التي لا تنعكس تلقائيًا.
- السمة تحفظ محليًا في المتصفح؛ أول تحميل يختار السمة المحفوظة أو تفضيل النظام.
- راعت الواجهة قارئات الشاشة، التركيز بلوحة المفاتيح، `Escape` وتقليل الحركة، وحالات انقطاع الاتصال.
- التفاعلات والردود شكلًا وتفاعلًا بصريًا لا تعني أنها مخزنة في الخادم.

## 12. تشغيل المشروع واختباره

### تشغيل محلي

المتطلبات الأساسية حسب إعداد المشروع: PHP 8.3+، Composer، PostgreSQL، وNode/npm لبناء CSS/JS. بعد إعداد `.env` وإنشاء قاعدة البيانات:

```powershell
composer install
php artisan key:generate
php artisan migrate --seed
npm install
npm run build
composer dev
```

`composer dev` يشغل مجموعة عمليات التطوير المعرفة في Composer؛ بديلًا يمكن تشغيل Laravel وReverb والـQueue وVite كلًا في terminal خاص. تأكد أن Google OAuth وReverb مهيآن إذا كنت تختبر الدخول والبث الحقيقيين.

### أوامر الفحص

```powershell
php artisan route:list
php artisan migrate:status
php artisan test
vendor\bin\pint --test
composer test:coverage
```

قياس التغطية يحتاج Xdebug أو PCOV مفعّلًا في **العملية التي تشغل الاختبارات**. في Windows قد لا تكفي خيارات `php -d` إذا أنشأ Artisan عملية PHP فرعية؛ إعداد `PHP_INI_SCAN_DIR` و`XDEBUG_MODE=coverage` قبل الأمر يسمح للعملية الفرعية برؤية Xdebug.

### ما الذي تختبره المجموعة؟

- `tests/Unit`: خدمات OAuth والرسائل، صلاحية المالك، شكل أحداث البث، واختيار اللغة.
- `tests/Feature/AuthApiTest.php`: إنشاء OAuth/الرمز، الملف الشخصي، وlogout.
- `tests/Feature/MessageApiTest.php`: التحقق والترقيم والصلاحيات والحذف والأحداث.
- `tests/Feature/BroadcastChannelTest.php`: دخول القناة للمستخدم المصادق ومنع الضيف.
- `tests/Feature/WebAuthTest.php`: جلسة المتصفح وتدفق OAuth.
- `tests/Feature/LivewireChatTest.php`: إرسال المحادثة وتعديلها وحذفها والمرشحات والردود والتفاعلات.
- `tests/Feature/LocalizationTest.php`: اللغة والاتجاه ورسائل الأخطاء.

`phpunit.xml` يحصر التغطية في `app/`، ويجبر الاختبارات على SQLite `:memory:` و`BROADCAST_CONNECTION=null`. لذلك تشغيل الاختبارات لا يهاجر قاعدة PostgreSQL المعتادة ولا يحتاج اتصال Reverb حقيقيًا. هذا عزل مقصود لحماية بيانات التطوير والإنتاج.

في آخر تشغيل موثق للمجموعة: **123 اختبارًا، 473 تأكيدًا**، و**95.04% تغطية أسطر**. تتغير الأرقام إذا تغيرت الشيفرة أو إعداد التغطية؛ أعد القياس قبل تقديمها كرقم حالي.

## 13. أجوبة قصيرة لأسئلة شائعة

**هل المشروع API فقط؟** لا؛ فيه REST API وواجهة Livewire للمتصفح، ويشتركان في الخدمات والسياسات والبيانات.

**هل كل مستخدم يرى البريد؟** لا؛ بيانات الكاتب داخل الرسائل لا تحتوي البريد. البريد موجود في مورد ملف المستخدم الحالي فقط.

**هل حذف الرسالة نهائي؟** لا؛ حذف الرسالة soft delete. لا تظهر بالاستعلامات المعتادة، لكنها تبقى مخزنة.

**هل WebSocket هو قاعدة البيانات؟** لا؛ PostgreSQL مصدر الحقيقة للرسائل. Reverb ناقل تحديثات لحظية.

**لماذا توجد جلسة وSanctum؟** الجلسة ملائمة لمتصفح same-origin وCSRF، بينما Sanctum bearer مناسب لعملاء API.

**لماذا simple pagination في الدردشة؟** لا تحتاج الواجهة إجمالي عدد الرسائل؛ تحتاج فقط معرفة وجود رسائل أقدم، فيتجنب `simplePaginate` استعلام العدد.

**هل شرط `toOthers()` يحفظ الرسالة؟** لا؛ الحفظ يحصل قبل بث الحدث داخل الخدمة، و`toOthers()` يمنع إعادة الحدث إلى المرسل فقط.

**لماذا اختبارات SQLite رغم PostgreSQL؟** لتكون سريعة ومعزولة وقابلة للتكرار ولا تغيّر قاعدة المطور؛ هذا لا يغني عن اختبار تكاملي منفصل على PostgreSQL.

## 14. مسار مذاكرة مقترح

1. اقرأ هذا الملف لتثبيت الصورة العامة.
2. افتح `routes/api.php` و`routes/web.php` وارسم الفرق بين الجلسة والرمز.
3. تتبع `AuthController` إلى `GoogleAuthService`، ثم ارسم دورة state يدويًا.
4. تتبع `MessageController::store` إلى `MessageService::send` ثم `MessageSent` و`MessageResource`.
5. تتبع `Chat::send` وفسر لماذا يستعمل `sendFromChat` المؤجل.
6. اقرأ `MessagePolicy` وجرّب شرح رفض تحديث رسالة مستخدم آخر.
7. قارن `paginate` بـ`paginateForChat`.
8. اشرح ما يُحفظ للرسالة وما لا يُحفظ للرد والتفاعل.
9. افتح الاختبار المطابق لكل إجابة؛ الاختبار دليل على السلوك المتوقع.
10. في النهاية، اقرأ [ملف التحضير للمناقشة](./التحضير-لمناقشة-المشروع.md) وأجب عن الأسئلة بصوت عالٍ دون النظر إلى الإجابات.
