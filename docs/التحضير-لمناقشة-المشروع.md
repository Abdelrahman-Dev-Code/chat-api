# التحضير لمناقشة مشروع المحادثة

هذا الملف للمراجعة الشفهية. حاول الإجابة أولًا بطريقتك، ثم قارن بإجابة النموذج. لا تحفظ الجمل حرفيًا؛ افهم المسار وأسماء الملفات والحدود الحالية.

## 1. عرض افتتاحي في دقيقة

> مشروعي تطبيق محادثة عامة مبني بـLaravel 13 وPHP 8.3. يوفر واجهة متصفح بـLivewire وREST API للعملاء الخارجيين. يستخدم Google OAuth لتأكيد الهوية؛ المتصفح يحتفظ بجلسة، والـAPI يحصل على Bearer token من Laravel Sanctum. الرسائل محفوظة في PostgreSQL، وتدار عملياتها المشتركة في MessageService، وتُحمى عمليات التعديل والحذف بسياسة MessagePolicy. بعد الكتابة تُبث أحداث الرسائل عبر قناة Reverb خاصة ويستقبلها المتصفح باستخدام Laravel Echo. اختبارات PHPUnit تستخدم SQLite داخل الذاكرة وتعطل البث لعزل الاختبارات عن الخدمات الخارجية. الردود والتفاعلات حاليًا معاينات واجهة غير محفوظة، وهذه نقطة تطوير مستقبلية واضحة.

## 2. أسئلة أساسية وإجابات مقترحة

### أ. ما المشكلة التي يحلها التطبيق؟

يوفر غرفة محادثة مشتركة، مع الدخول بحساب Google، إرسال الرسائل وعرضها وتعديل رسائل المستخدم أو حذفها، وتحديث مباشر للمستخدمين المتصلين. كما يوفر API ليتمكن عميل غير المتصفح من تنفيذ عمليات الرسائل بنفس قواعد العمل.

### ب. اشرح المعمارية من HTTP إلى قاعدة البيانات.

يصل الطلب إلى Route. تطبق Laravel middleware المصادقة واللغة وغيرهما. في API يتحقق Form Request من المدخلات. Controller ينسق الطلب ويستدعي Service. Service ينفذ حالة الاستخدام باستخدام Models/Eloquent. عند النجاح يعيد Controller Resource أو status code، وقد ينشأ Event للبث. في واجهة الويب ينفذ Livewire الإجراء ويحدث Blade؛ الأعمال المشتركة ما زالت تمر بالخدمات والسياسات.

**ترتيب يسهل تذكره:**

```text
Route → Middleware → Request validation → Controller/Livewire
      → Policy (عند الحاجة) → Service → Model/Database
      → Resource/Livewire response + Event
```

### ج. لماذا يوجد Service layer؟

حتى لا تتكرر قواعد إنشاء الرسالة وتحديثها وحذفها بين Controller وLivewire. `MessageService` مكان استخدام مشترك، ويسمح باختبار السلوك منفصلًا. Controller يظل مسؤولًا عن HTTP، وLivewire يظل مسؤولًا عن حالة الشاشة.

### د. ما دور Form Request وResource؟

- `SaveMessageRequest` يتحقق من أن المحتوى موجود ونصي ولا يتجاوز 2000 محرف، ويوفر القاعدة نفسها لـLivewire.
- `ListMessagesRequest` يتحقق من `page` و`user_ids[]`.
- `MessageResource` ينشر عقد JSON ثابتًا ومحدودًا بدل كشف كل أعمدة Eloquent.

### هـ. كيف تمنع المستخدم من تعديل رسالة غيره؟

`MessagePolicy` تقارن `user_id` بالهوية المصادق عليها عبر `isAuthoredBy`. مسارات API تستخدم authorize على update/delete، وLivewire يستخدم Gate قبل عمليات التعديل والحذف. هذا تحقق خادمي؛ إخفاء الزر في الواجهة وحده ليس حماية.

### و. كيف تعرف الخدمة هوية كاتب الرسالة؟

من المستخدم المصادق عليه، وليس من `user_id` يرسله العميل. API يستخدم المستخدم الذي وفره Sanctum، وLivewire يستخدم المستخدم في الجلسة. لذلك لا يستطيع العميل انتحال كاتب بمجرد تعديل جسم الطلب.

## 3. أسئلة OAuth وSanctum

### ز. اشرح تسجيل الدخول بـGoogle خطوة خطوة.

الخادم يصنع state عشوائيًا ويحفظه في Cache بعمر عشر دقائق؛ العميل لا يختار هوية المستخدم. يذهب المستخدم إلى Google، ثم يعود authorization code. الخادم يستبدل code مع Google server-to-server، ويتحقق أن البريد موثق، ثم يطابق Google ID أو البريد الموثق أو ينشئ مستخدمًا جديدًا.

### ح. ما فائدة `state`؟

حماية OAuth من تزوير callback وCSRF وإعادة تشغيل الحالة. الحالة أحادية الاستخدام لأن الخدمة تسحبها من Cache بـ`pull`، ولها مهلة انتهاء. في الويب تخزن بصمة سياق جلسة المتصفح وتقارن عند العودة، فيمنع إتمام تسجيل دخول بدأ في جلسة أخرى.

### ط. ما الفرق بين تسجيل دخول الويب وAPI؟

تدفق الويب يستخدم session guard وcookie ويعيد توجيه المستخدم إلى `/chat`. تدفق API يعيد رمز Sanctum في JSON ويستخدمه العميل في `Authorization: Bearer ...`. الويب يحتاج CSRF لطلبات الجلسة؛ والرمز يجب حفظه في العميل بسرية.

### ي. ماذا يفعل logout؟

- `POST /logout` ينهي جلسة الويب ويبطلها ويجدد CSRF token.
- `POST /api/auth/logout` يحذف token المستخدم الحالي فقط. لا يعني ذلك حذف كل tokens التابعة للحساب.

### ك. هل التطبيق يخزن كلمة مرور Google؟

لا. يسجل المستخدم بمعرّف Google والبريد وبيانات الملف العام اللازمة. عمود password اختياري/nullable لأن تسجيل Google لا يحتاج كلمة مرور محلية.

### ل. لماذا البريد لا يظهر مع كل رسالة؟

لأن الرسالة تستخدم `UserResource` العام الذي يعيد id/name/avatar فقط. `ProfileResource` يضيف البريد للمستخدم صاحب الطلب فقط. هذا مبدأ أقل قدر من البيانات.

## 4. أسئلة الرسائل وقاعدة البيانات

### م. صف جدول الرسائل وعلاقته.

جدول `messages` يحوي id و`user_id` ومحتوى نصيًا وtimestamps و`deleted_at`. المفتاح الأجنبي يربط كل رسالة بمستخدم، وEloquent يعرف `Message belongsTo User` و`User hasMany Message`. هناك فهارس للتاريخ وللكاتب مع التاريخ لتسريع استعلامات القائمة والتصفية.

### ن. ما معنى soft delete؟

بدل حذف صف الرسالة، تسجل Eloquent وقت الحذف في `deleted_at`. الاستعلامات العادية تستبعد الرسائل المحذوفة، ويمكن نظريًا استعادتها أو مراجعتها عبر الاستعلامات التي تشمل المحذوفات. الحدث الذي يخبر العملاء بالحذف يرسل ID فقط.

### س. ما قواعد محتوى الرسالة؟

محتوى مطلوب، string، وطوله الأقصى 2000. تستخدم REST وLivewire القاعدة المشتركة `SaveMessageRequest::contentRules`. Laravel يزيل الفراغات المحيطة/يحول النص الفارغ، لذلك لا يمر النص المكون من مسافات.

### ع. كيف تعمل pagination؟

REST يستعمل `paginate(10)` ويعيد metadata مثل الإجمالي والروابط؛ يعرض API أحدث الرسائل أولًا. الدردشة تستخدم `simplePaginate(10)` لتفادي count query غير اللازم، ثم تقلب ترتيب عناصر الصفحة للعرض من الأقدم للأحدث. تحميل القديم يضيفه أعلى السجل ويحافظ على موضع التمرير.

### ف. لماذا هناك `MessageResource` إذا كانت البيانات موجودة في Model؟

الـResource يفصل واجهة البيانات عن المخطط الداخلي. يحدد بالضبط ما يظهر للعميل، ويمنع كشف حقول غير مقصودة، ويسمح بتغيير قاعدة البيانات دون تغيير عقد JSON لكل تعديل داخلي.

### ص. هل API يدعم كل مرشحات الواجهة؟

لا. بحسب Request الحالي يدعم API الصفحة و`user_ids[]` فقط. واجهة Livewire لديها مرشحات نص وتاريخ ومرسل و«رسائلي فقط». لا أفترض أن دعم الواجهة موجود تلقائيًا في REST؛ يجب إضافة قواعد request واستدعاء service المناسب واختبارات API إذا أريد ذلك.

## 5. أسئلة Reverb والاتصال اللحظي

### ق. لماذا نحتاج Reverb إذا كانت الرسالة محفوظة في PostgreSQL؟

قاعدة البيانات تحفظ الحالة الدائمة. Reverb ينقل إشعار التغيير للمستخدمين المتصلين في الوقت الفعلي. إذا انقطع WebSocket، لا يعني أن الرسالة لم تُحفظ؛ يمكن للعميل إعادة تحميل السجل من API/Livewire.

### ر. ما وظيفة Laravel Echo؟

Echo عميل JavaScript يشترك في قناة Reverb ويستمع للأحداث. `chat-app.js` يهيئ Echo على صفحة المحادثة، و`Chat` يربط `message.sent`, `message.updated`, `message.deleted` بتحديث الحالة المرئية.

### ش. لماذا القناة private؟

لأن دخولها يجب أن يمر من endpoint تفويض. الجلسة تستخدم `/broadcasting/auth`، والـAPI يستخدم `/api/broadcasting/auth` مع Sanctum. بعد المصادقة، قناة `chat` الحالية تسمح لكل المستخدمين المصادقين، لأنها غرفة عامة مشتركة داخل التطبيق وليست غرفة شخصية.

### ت. ماذا يعني `toOthers()`؟

يمنع إرسال broadcast إلى اتصال المرسل نفسه، لتجنب ظهور نسخة مزدوجة. المرسل يحدّث واجهته محليًا بعد نجاح الحفظ؛ أما المشتركين الآخرون فتصلهم نسخة الحدث.

### ث. كيف يمنع النظام اختلاف بيانات حدث الإرسال عن الرسالة بعد تعديل سريع؟

`MessageEvent` يلتقط payload كـsnapshot عند إنشاء الحدث. فلا يعتمد على إعادة قراءة نموذج ربما تغير لاحقًا قبل تنفيذ البث.

### خ. ما الذي يحدث إذا فشل Reverb؟

تبقى الرسالة المحفوظة في قاعدة البيانات؛ البث ليس هو التخزين. مسار Livewire يؤخر البث حتى بعد الاستجابة ويحاول تسجيل فشل broadcast، والواجهة تعرض حالة الاتصال/إعادة الاتصال. لا ينبغي الادعاء أن نجاح websocket شرط لنجاح الكتابة.

### ذ. لماذا قد لا يعمل Reverb عند إتاحة Laravel على الشبكة المحلية؟

لأن عنوان HTTP وعنوان WebSocket إعدادان منفصلان. يجب أن يصل المتصفح إلى عنوان `REVERB_PUBLIC_HOST/PORT/SCHEME`، وأن يستطيع Laravel الوصول إلى `REVERB_HOST/PORT`. كما يجب ضبط callback URLs في Google و`APP_URL` والجدار الناري. تشغيل Laravel على `0.0.0.0` لا يعدل إعدادات Reverb تلقائيًا.

## 6. أسئلة Livewire والواجهة

### ض. ما دور `Chat`؟

مكوّن Livewire يملك حالة الصفحة: الرسائل المعروضة، رقم الصفحة ووجود قديم، فلاتر البحث والتاريخ والمرسل، مسودة الكتابة، التحرير، التفاعلات، والرد المؤقت. ينفذ إجراءات الشاشة ويستدعي الخدمة والسياسات، لكنه لا يستبدل API ولا قاعدة البيانات.

### ظ. لماذا لا تعرض الواجهة كل الرسائل مرة واحدة؟

تقلل الترقيم كمية البيانات والرسم الأولي. الصفحة الأولى 10 رسائل، ويمكن تحميل السابق عند الطلب. يحسن ذلك وقت التحميل والذاكرة مع سجل أكبر.

### غ. كيف تتصرف الواجهة عند وصول رسالة جديدة؟

تقارن الرسالة بالمرشحات الحالية؛ لا تضيف ما لا يطابقها. تدمج الرسالة حسب ID وترتبها زمنيًا، وتتجاهل echo المحلي. إذا كان المستخدم عند نهاية السجل تنزل تلقائيًا؛ وإلا تظهر زر رسائل جديدة حتى لا تقاطعه أثناء القراءة.

### أأ. هل الردود والتفاعلات محفوظة؟

لا. الرد يضيف quote preview إلى حالة Livewire محلية، والتفاعل يحفظ قائمة مؤقتة في حالة المكون. لا توجد migrations أو endpoint أو event مخصص لها. التحديث قد يمحوها، والمستخدمون الآخرون لا يحصلون على تفاعل مستمر. أقول ذلك بصراحة بدل وصفها كميزة مكتملة.

### بأ. كيف تُحفظ اللغة؟

`LocaleController` يتحقق من أن اللغة مدعومة، ويضعها في الجلسة وcookie طويلة العمر. `SetLocale` يختار اللغة بأولوية session ثم cookie ثم Accept-Language ثم default، ويطبقها على Carbon. اللغتان الموجودتان هما العربية والإنجليزية.

## 7. الاختبارات والجودة

### جأ. لماذا الاختبارات لا تستخدم PostgreSQL؟

`phpunit.xml` يفرض `DB_CONNECTION=sqlite` و`DB_DATABASE=:memory:`، ويجعل البث null. هذا يجعل الاختبارات معزولة وقابلة للتكرار ولا تعبث بقاعدة المطور. لكنه لا يثبت وحده سلوك كل خصائص PostgreSQL؛ يجب إجراء اختبار تكاملي منفصل على نسخة اختبار من PostgreSQL عند الحاجة.

### دأ. ما الفرق بين Unit وFeature tests هنا؟

- Unit tests تركز على خدمة أو سياسة أو حدث في نطاق أصغر، مثل تطبيع الحساب أو صلاحية المالك.
- Feature tests تمر عبر HTTP/Laravel أو Livewire وتفحص النتيجة كاملة: status، JSON، قاعدة البيانات، الجلسة، البث، والرسائل المعروضة.

### هأ. كيف أتحقق من المشروع؟

```powershell
php artisan test
vendor\bin\pint --test
php artisan route:list
php artisan migrate:status
```

التغطية:

```powershell
composer test:coverage
```

تتطلب Xdebug أو PCOV مفعّلًا لدى PHP الذي يشغل PHPUnit. آخر تحقق موثق: 123 اختبارًا و473 assertion، وتغطية أسطر 95.04%. لا أخلط هذه النسبة بتغطية الطرق أو الفئات؛ القياس السابق أظهر أن تغطية الأسطر أعلى منهما.

## 8. مواقف عملية قد تُطرح

### «مستخدم حاول حذف رسالة لغيره، ماذا يحصل؟»

يفشل قرار `MessagePolicy`؛ لا تستدعي الخدمة الحذف ولا ينشأ حدث `MessageDeleted`. REST يرجع 403، والواجهة تعرض خطأ صلاحية. يوجد اختبار API واختبار Livewire لهذا السلوك.

### «تم إرسال الرسالة لكن المتصفح الآخر لم يرها فورًا؛ هل ضاعت؟»

ليس بالضرورة. أتحقق أولًا من قاعدة البيانات، ثم اتصال Reverb وEcho والقناة الخاصة وعنوان العميل. الرسالة قد تكون محفوظة حتى مع تعطل البث؛ إعادة تحميل السجل تعيد قراءتها.

### «لماذا حذف الرسالة لا يرسل محتواها؟»

المشترك يحتاج معرّف الرسالة كي يزيلها من الشاشة. إرسال المحتوى بعد الحذف غير ضروري ويزيد البيانات المكشوفة في الحدث.

### «كيف أضيف الردود لتصبح حقيقية؟»

أحدد العقد أولًا: هل الرد مرتبط برسالة في الغرفة نفسها؟ ثم أضيف migration بـ`reply_to_message_id` وforeign key مناسب، relation في Model، policy للتحقق من صلاحية عرض الهدف، validation يمنع الرد على رسالة محذوفة أو غير مسموحة، resource يضم مقتطف الرد، service يطبق القاعدة، API وLivewire يستعملان الخدمة، وأحداث البث تحمل snapshot موحدًا. أخيرًا أضيف اختبارات للصلاحيات والحذف والهدف المفقود والتزامن، وأفكر في ترحيل/عرض الردود القديمة. لا أكتفي بإضافة حقل في الواجهة.

### «كيف أجعل التفاعلات دائمة؟»

أحتاج جدولًا مثل `message_reactions` يحوي message_id وuser_id وemoji مع قيد فريد يمنع تكرار نفس تفاعل المستخدم على الرسالة، وسياسة تحقق، endpoints/service وحدث بث وتحديث الواجهة المتزامن، إضافة إلى اختبارات الإضافة والإزالة والتكرار وحذف الرسالة.

## 9. نقاط قوة ونقاط تطوير أعرضها بصدق

### نقاط قوة

- واجهة وAPI يشتركان في خدمة حالات استخدام الرسائل.
- OAuth يستخدم state أحادي الاستخدام، ويتحقق من البريد الموثق.
- فصل هوية الكاتب عن بيانات الطلب.
- سياسة الصلاحيات تطبق على الخادم لكلا الواجهتين.
- API Resources تحد البيانات المعروضة.
- حذف الرسالة ناعم؛ pagination محددة؛ البث يلتقط snapshot.
- اختبارات تغطي المصادقة والـAPI والواجهة والقناة والصلاحيات.

### حدود أو أعمال مستقبلية

- الردود والتفاعلات previews فقط وليست بيانات دائمة.
- الـAPI لا يعرض حاليًا مرشحات البحث والتاريخ المتاحة في الواجهة.
- حد معدل إرسال Livewire لا يعني وجود حد مماثل على API messages.
- يحتاج البث إلى Reverb وQueue حسب إعداد البيئة، ويجب مراقبة فشل الخدمات الخارجية.
- إعداد Reverb الحالي يسمح بمصدر `*` في `config/reverb.php`; ينبغي تقييده في الإنتاج.
- يجب التحقق على PostgreSQL في CI/اختبار تكاملي، لأن PHPUnit يستخدم SQLite.

## 10. مصطلحات سريعة

| المصطلح | معناه في هذا المشروع |
|---|---|
| OAuth | تفويض تسجيل الدخول لدى Google دون أن يتعامل التطبيق مع كلمة مرور Google |
| `state` | قيمة عشوائية مؤقتة تربط بدء OAuth بالـcallback وتحمي من تزويره |
| Sanctum | إصدار والتحقق من API bearer tokens |
| Session | حالة تسجيل الدخول الخاصة بالمتصفح |
| Middleware | طبقة تعالج الطلب قبل وصوله إلى منطق route |
| Form Request | قواعد تحقق منظمة لمدخلات HTTP |
| Policy | قرار صلاحية مستخدم على مورد |
| Eloquent | ORM Laravel للتعامل مع الجداول والعلاقات |
| Resource | محول يحدد شكل JSON العام |
| Soft delete | علامة حذف مؤقتة عبر `deleted_at` دون إزالة الصف مباشرة |
| Private channel | قناة بث لا يدخلها العميل إلا بعد تفويض |
| Reverb | خادم WebSocket الخاص بـLaravel |
| Echo | مكتبة JavaScript للاشتراك بالأحداث |
| `toOthers()` | البث للجميع عدا الاتصال الذي أرسل الحدث |
| `simplePaginate` | ترقيم يتجنب حساب عدد النتائج الإجمالي |

## 11. مراجعة سريعة قبل المناقشة

- [ ] أستطيع شرح الفرق بين جلسة الويب وSanctum token.
- [ ] أستطيع رسم OAuth state وتدفق التحقق من البريد.
- [ ] أعرف مسار `POST /api/messages` من Route إلى Event.
- [ ] أستطيع شرح من يحدد `user_id` ولماذا لا يأتي من body.
- [ ] أميز بين validation وauthorization.
- [ ] أشرح الفرق بين pagination للـAPI وpagination للدردشة.
- [ ] أشرح private channel ولماذا هي غرفة مشتركة.
- [ ] أعرف ما الذي يبثه كل حدث وماذا يحدث عند `toOthers()`.
- [ ] أقول بوضوح إن الردود والتفاعلات مؤقتة.
- [ ] أشرح لماذا الاختبارات تستخدم SQLite و`BROADCAST_CONNECTION=null`.
- [ ] أذكر نسبة التغطية مع توضيح أنها نسبة الأسطر وفي آخر قياس.
- [ ] لا أعرض `.env` أو tokens أو Google/Reverb secrets أثناء العرض.
